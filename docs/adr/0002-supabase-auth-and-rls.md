# ADR-0002: Supabase Auth 채택과 RLS를 인가의 주 수단으로 삼는 결정

- Status: **accepted** — 사용자 결정 2026-08-04 (게이트 항목 ②③⑤. architect 권고안 그대로 승인, 수정 없음)
- Date: 2026-08-04 (제안) · **2026-08-04 (승인)**
- Owner: architect
- DECISIONS.md entry: #3, #4, #5, **#31(승인 기록 + 무료 티어 한도 measured 근거)**

## Context

- **Planning Decision #30**: *"간단 로그인을 MVP에 포함한다. **Supabase Auth 활용 여부 판단은 architect 몫**."* — 이 ADR이 그 판단이다.
- **Planning Decision #86 / AC-060**: 비밀번호는 **최소 8자, 추가 복잡도 규칙 없음**. 그리고 *"실제 인증 수단이 자체 정책을 강제하는 경우 **그 정책이 8자 최소를 만족하는지만 확인**하고 별도 검증을 중복 구현하지 않는다(구현 판단은 architect)."*
- **AC-039**: *"로그인한 사용자별로 프로필·쌍방 규약·diff 히스토리·용어사전이 분리되어 저장되며, **다른 사용자의 데이터가 조회되지 않는다(계정 2개로 교차 확인)**."*
- **Planning Decision #43**: 인증(T45·T46)은 **P1**이며 T18(스토리지)보다 **먼저** 완료해야 한다.
- **Planning Decision #42/#62 컷 순서 ⑤(갱신 후 ④)**: **"로그인 고도화"가 컷 대상**이다 — 기본 로그인·세션을 넘는 것(비밀번호 재설정·계정 관리)은 잘라낼 수 있다.
- PRD Constraints: *"저장소는 Supabase(프로필, diff 히스토리, 용어사전)."*
- Risks 표: *"문화 프로파일링 … 프로필은 본인 소유이며 관리자에게 노출하지 않는다는 원칙."*

즉 **"인증을 직접 만들 것인가"** 와 **"타 사용자 데이터 미조회를 무엇이 보장하는가"** 두 질문이 함께 걸려 있다.

## Decision

**① 인증은 Supabase Auth(이메일+비밀번호)를 쓰고 자체 구현하지 않는다. ② 인가는 애플리케이션 `where` 절이 아니라 Postgres RLS로 DB 레벨에서 강제한다. ③ 비밀번호 최소 8자는 Supabase 설정에서만 지정하고 앱에 복잡도 검증을 만들지 않는다.**

| Option | Pros | Cons |
|---|---|---|
| **Supabase Auth + RLS** ✅ | 가입·로그인·로그아웃·세션 갱신이 **우리 코드 거의 0**. `@supabase/ssr` 이 HttpOnly 쿠키를 관리한다. **RLS가 `auth.uid()` 를 그대로 쓸 수 있다** — 인증과 인가가 같은 스택이라 접합부가 없다. Free 티어에 **50,000 MAU**(measured, supabase.com/pricing 2026-08-04 직접 열람)로 한도 걱정이 없다. Planning Decision #86의 "중복 구현하지 않는다"를 문자 그대로 만족 | 인증 방식이 벤더에 묶인다. 비밀번호 정책이 **대시보드 설정**이라 코드 리뷰로 보이지 않는다 — 설정 스크린샷/실행 출력이 근거가 되어야 한다 |
| 자체 인증 (bcrypt + JWT 또는 세션 테이블) | 벤더 비종속. 정책이 코드에 보인다 | **[BE-B] 1~2일.** T45는 **P1이고 컷 순서의 대상**이다 — 잘라낼 수도 있는 기능에 비밀번호 해싱·세션 회전·토큰 무효화라는 보안 표면을 우리가 진다. 게다가 RLS를 쓰려면 우리 JWT를 Postgres가 이해하도록 별도 배선이 필요해져 **②가 더 비싸진다** |
| Auth.js(NextAuth) + Supabase DB | Next.js 관용구. 소셜 로그인 확장 용이 | 세션은 Auth.js가, 데이터는 Supabase가 관리해 **`auth.uid()` 가 자동으로 채워지지 않는다** — RLS를 쓰려면 JWT 브리지를 직접 만들어야 한다. 소셜 로그인은 PRD에 없다 |
| 인가를 애플리케이션 `where` 절로 | 디버깅이 쉽다 | 🔴 **AC-039를 사람의 주의력에 맡긴다.** 라우트 20여 개 중 한 곳에서 `where owner_user_id = …` 를 빠뜨리면 그것이 곧 유출이고, 리뷰에서 20곳을 매번 확인해야 한다 |

### 정책 형태 (전 테이블 동일 패턴 1개 + 예외 1개)

```sql
-- 사용자 소유 테이블 7개 공통
USING (owner_user_id = auth.uid())  WITH CHECK (owner_user_id = auth.uid())
-- 예외: pair_protocols 는 한 쌍 1행이며 양측이 열람·수정 (AC-037)
USING (auth.jwt()->>'email' IN (party_a, party_b))
-- 예외: llm_cache / llm_call_log 는 RLS 활성 + 정책 0개 = 서비스 롤 전용
```

## Consequences

- **Positive**
  - T45(인증)가 **화면 2개 + 설정**으로 끝나 Planning Decision #43의 "M2 첫 태스크"를 실제로 지킬 수 있다.
  - AC-039가 **DB 레벨에서 보장**된다. 라우트를 추가할 때마다 인가를 다시 생각하지 않아도 된다.
  - AC-060의 "복잡도 규칙 없음"이 **우리가 아무것도 만들지 않음**으로 달성된다 — 없는 검증을 안 만드는 것이 가장 확실한 준수다.
  - 컷 순서 ④("로그인 고도화")를 실행할 때 지울 것이 **우리 코드가 아니라 안 쓰는 기능**이라 컷 비용이 0에 가깝다.
- **Negative / 수용한 대가**
  - **벤더 종속.** 다른 DB로 옮기면 인증도 함께 옮겨야 한다.
  - **RLS 디버깅이 어렵다** — 정책이 틀리면 "0행이 반환되는데 이유가 안 보인다". 완화: 정책을 위 3패턴으로만 제한하고 예외를 늘리지 않는다.
  - **비밀번호 정책이 코드에 없다.** 대시보드 설정이므로 근거를 실행 출력으로 남겨야 한다.
  - ⚠️ **Supabase의 최소 비밀번호 길이를 8로 설정 가능한지는 이번 세션에 확인하지 않았다(추정).** 기본값이 8보다 낮을 수 있다.
- **Follow-ups required**
  1. **T45 착수 시(추정 항목 해소)**: Auth 설정에서 최소 길이를 **8**로, 문자 요구사항을 **끔**으로 두고, ⓐ 7자 거부 ⓑ 8자 허용 ⓒ `aaaaaaaa` 통과 **3건을 실제로 실행해 출력을 첨부**한다(AC-060의 판정 방법 그대로). **8 설정이 불가하면 즉시 보고**하고 대안(앱 레벨 최소 길이 검증 1줄만 추가)을 결정한다.
  2. **T45**: 연속 로그인 실패 10회를 시도해 Supabase 기본 rate limit 동작을 관찰·기록한다(Security 절의 추정 항목).
  3. **T18**: 마이그레이션 0001에 **전 테이블 RLS ENABLE + 정책**을 포함하고, **계정 2개로 교차 확인**한 0행 조회 출력을 AC-039 근거로 첨부한다.
  4. **T3**: `SUPABASE_SERVICE_ROLE_KEY` 사용처를 `llm_cache`·`llm_call_log` **2곳으로 제한**하고, 그 외에서 서비스 롤 클라이언트를 만들지 않는다(RLS 우회 키이므로).

## Follow-up (2026-08-12) — "로그인 고도화" 컷 범위를 비밀번호 재설정만 부분적으로 되돌린다

- **Status**: accepted — 사용자 결정 2026-08-12 (PRD Planning Decision #130, AC-090)
- 본문의 Planning Decision #42/#62 인용("로그인 고도화가 컷 대상") **원문은 수정하지 않는다** — 이 절은 그 컷 범위 중 한 조각만 좁히는 후속 결정이다.

**결정**: 새 디자인 handoff 로그인 목업을 실제 구현과 대조하다 이 컷 결정을 다시 발견했다. 사용자에게 확인한 결과:
- **비밀번호 재설정**: 지금 구현한다. Supabase Auth 내장 기능(`resetPasswordForEmail()` / `updateUser({ password })`)만으로 완결되고, 새 외부 의존성·자격증명이 필요 없다 — ①의 "인증은 Supabase Auth를 쓰고 자체 구현하지 않는다" 원칙을 그대로 따르는 범위 확장이며, 이 ADR이 채택한 옵션(Supabase Auth + RLS)의 경계를 벗어나지 않는다.
- **SSO(회사 계정으로 계속하기)**: 계속 제외한다. 실제 외부 ID 공급자(Google Workspace/Okta 등) 클라이언트 ID·시크릿이 없고, 이 ADR의 Option 비교표가 이미 "소셜 로그인은 PRD에 없다"고 명시했다 — PRD 자체를 먼저 개정하고 실제 IdP를 계약하지 않는 한 착수할 수 없다.

**최소 비밀번호 길이**: ①에서 아직 "추정"으로 남겨둔 8자 하한(`⚠️ Consequences` 행)을 이번 절이 확정한 것은 아니다 — `/reset-password`의 클라이언트 검증은 그 추정치(8자)를 그대로 재사용하되, Supabase 대시보드 실제 설정값과의 일치 여부는 여전히 별도 follow-up(위 Follow-ups required 1번)에 속한다.

**영향받지 않는 것**: RLS 정책, 세션 관리(`@supabase/ssr`), 가입/로그인/로그아웃 로직 — 전부 이 절 이전과 동일하다.
